# ADR-0006: Общая авторизация макропортала (core.auth)

Статус: accepted
Дата: 2026-08-25

## Контекст

Библиотека — первый модуль личного макропортала. В дальнейшем появятся другие сервисы/модули с общей авторизацией (мастер-промпт §11.2, §12). Требование пользователя: авторизация должна работать для текущего портала и быть основой авторизации всего макропортала.

## Решение

1. **auth живёт в `portal.core.auth`** — уровне портала, не модуля library. Library не имеет собственных пользователей, логинов и сессий; она получает личность через зависимости FastAPI (`CurrentUser`, `OptionalUser`, `require_scope`).

2. **Модель токенов** (мастер-промпт §12):
   - Access: JWT (HS256, TTL 15 мин), claims: `sub`, `jti`, `scopes`, `typ`.
   - Refresh: opaque-токены (`prt_…`), в БД только SHA-256-хэш, ротация при каждом обновлении, отзыв при logout, TTL 30 дней, cookie Path=/auth.
   - Device: opaque (`pdt_…`), scope `library:opds:read`, TTL 365 дней — готовы для OPDS/FBReader (Phase 7), показываются один раз.
   - Scopes: `portal:full` для интерактивных сессий; узкие scope для устройств/сервисов.

3. **Готовность к нескольким сервисам**:
   - Потребители зависят только от интерфейса `TokenService.verify()` / `TokenPrincipal` — при переходе на RS256/JWKS меняется только этот модуль.
   - Сегодня: общий секрет (HS256) через `LIBRARY_JWT_SECRET` — достаточно для модулей одного процесса/хоста.
   - Когда появится второй сервис на отдельном домене: перейти на асимметричные ключи (RS256/EdDSA) + JWKS-эндпоинт `/.well-known/jwks.json` в core.auth; сервисы верифицируют публичным ключом. Интерфейс потребителей не меняется.
   - Cookie-based SSO между поддоменами `*.gorbunovr.ru` — возможен через общий домен cookie; решение отложено до появления второго web-сервиса (OPEN_QUESTIONS).

4. **Регистрация**: bootstrap — первый пользователь становится owner/superuser; далее регистрация закрыта (создание аккаунтов только superuser'ом). Логин: email+password (argon2id).

5. **Web-сессии**: access+refresh в HttpOnly SameSite=Lax cookies (Secure в prod); CSRF double-submit (`library_csrf` cookie + `x-csrf-token` header) для cookie-аутентифицированных unsafe-запросов; Bearer-запросы CSRF не требуют.

6. **Аудит**: register/login/login_failed/refresh/logout/device_token_* пишутся в `audit_log`; failure-события — отдельной транзакцией (не откатываются вместе с основной операцией).

7. **Rate limiting**: in-memory sliding window (login 5/мин на IP+email, register 3/мин на IP). Однопроцессный — при масштабировании вынести в общее хранилище (TECH_DEBT).

## Последствия

- Новый модуль макропортала = новый router + `owner_id` в своих таблицах + зависимости из core.auth. Ноль дублирования логина.
- Смена секрета инвалидирует все access-токены (refresh живут в БД и переживают ротацию секрета).
- tracker.gorbunovr.ru (существующий сервис со своей auth) НЕ мигрируется автоматически — вопрос отдельный (OPEN_QUESTIONS).
